# Development lifecycle

Whenever you are given a task which is of the form "something is wrong" or "I want something to
exist but it doesn't", consider whether it makes sense to write a failing test or a repro script. If
either or both of those make sense, write them and commit before proceeding to any sort of "fix" or
"feature implementation". The test/repro must pass if and only if the fix/implementation is in
place; it should be possible to verify this by reverting the latter.

When writing tests, consider only how things should behave. Do not avoid writing a test because the
assertion would fail given the current impl. Never weaken, remove, or disable a test in order to
make the test go green, even if it's in a PR that I plan to merge: failing tests are a gift, not a
problem; they tell us how to fix the implementation.

It is not the case that tests should always pass at every commit because, we will typically commit
failing tests to repro a bug before committing the fix in a subsequent commit. This permits using
`git checkout` and/or `git revert` to verify the fundamental invariant: that tests pass if and only
if no incorrectness in implementation is known at that commit.

Never manually edit autogenerated files. Be Bayesian. The right command (e.g. a Makefile command)
should exist and be fairly obvious; if it doesn't, that's a reason to stop and ask me for advice.

Never open PRs in non-draft mode. If I say "create a PR for it" I probably just mean create the
local commit that I'll push. Always confirm with me.

# How to write prose

You have been trained to write prose in a way that is more flowery, metaphorical, and pretentious
than I want. Here are some examples of real output that I have had to correct:

BAD: "a workflow activity has no per-activity start delay, so neither a config nor a trace can name one"
GOOD: "workflow activity does not support start delay"

BAD: "irreducible floor" "the residue" "the crux" "wart" "escape hatch" "where the amortization lands" "burns no retries" "rides on the item"

Don't say that something 'names' something. Software engineers rarely use that word. A model
can or cannot 'express' something; in general 'contains' or 'uses' is often the right word.

Avoid inventing terms and then using your own terms. Similarly, avoid referring to sections in
documents other than the current purely by a section number. The problem in both cases is that while
your own internal implementation is good at retrieving information by arbitrary keys, human brains
don't work like this: humans need a little semantic reminder to "jog their memory", and they would
prefer not to learn new keys introduced by agent output.

When writing commit message the first line must say what problem it solves or why it is an improvement.

When writing comments do not write to sell the code: instead be unflinchingly honest and if there
are deficiencies say so simply and directly.

If the truth is that something is suboptimal then say that explicitly. Never write about a
suboptimality that leaves a reader wondering whether you are saying "there's a problem" or
"everything is fine". In other words, never sell. Never in comments, never in GitHub READMEs; never.
I'm a software engineer, not a salesperson.

When you are ready to commit, read over all prose, check these rules, and rewrite any violations.
